# TIL: Supply Chain Security: SLSA Framework

*Date: 2026-10-21*

## Summary / Problem Statement

Modern software rarely ships without dozens of third-party dependencies, build tools, and CI/CD pipelines — each one a potential attack vector. The 2020 SolarWinds breach and the 2021 `codecov` compromise demonstrated how a single tampered build step can silently poison thousands of downstream consumers. **SLSA (Supply-chain Levels for Software Artifacts)**, pronounced *"salsa"*, is a security framework from Google (now a joint OpenSSF project) designed to systematically harden this attack surface.

---

## Key Concepts & Technical Details

**SLSA defines four progressive levels of supply chain integrity:**

- **SLSA 1** — Build process is documented and produces **provenance** (a signed metadata record describing *who* built *what*, *when*, and *how*).
- **SLSA 2** — Provenance is generated by a **hosted build service** (e.g., GitHub Actions, Google Cloud Build), making it harder to forge.
- **SLSA 3** — The build service itself is **hardened and audited**; the build environment is isolated and ephemeral, preventing tampering mid-build.
- **SLSA 4** *(now split into SLSA 4 under v0.1, reorganized in v1.0)* — **Two-party review** of all build scripts plus hermetic, reproducible builds.

**Core artifact: the Provenance Document**

- Follows the **in-toto Attestation Framework** format.
- Signed using **Sigstore / cosign**, enabling keyless signing via OIDC identity.
- Verifiable with tools like `slsa-verifier` before consuming an artifact.

**Key threats addressed per level:**

| Threat | Mitigated at |
|---|---|
| Tampered source code | SLSA 2+ |
| Compromised build script | SLSA 3 |
| Rogue build admin | SLSA 3+ |
| Reproducibility gaps | SLSA 4 |

---

## Practical Takeaway / Real-world Gotcha

> **Gotcha:** Generating provenance is not the same as *verifying* it.

Many teams adopt SLSA tooling to *produce* attestations but never wire up verification in their deployment pipelines. An attacker can still swap a binary if nothing downstream checks the signature.

- Always run `slsa-verifier verify-artifact` (or equivalent) as a **pipeline gate**, not just an audit step.
- Start at **SLSA Level 1** today — even basic provenance dramatically improves incident response by answering "what exactly got deployed?"
